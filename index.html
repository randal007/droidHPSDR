droidHPSDR

An Android SDR transceiver front end for OpenHPSDR Protocol 1 and 2 radios, with a focus on the Hermes Lite 2 / 2+.

Forked from deskHPSDR (DL1BZ), itself forked from piHPSDR (DL1YCF). GPL v3 or later.

Repository README Issues
Pre-alpha. Nothing works yet. This repository is design notes and scaffolding. Do not expect a build. Do not expect an APK. Watch the repo if you want to know when Milestone 1 lands.

Why

deskHPSDR is a mature, WDSP-based transceiver front end aimed squarely at desktop macOS and Linux, with a 1280×600 minimum screen size and a mouse-oriented GTK3 UI. It is explicitly not targeting small screens or mobile.

SDR++ Brown already runs on Android and supports the HL2 with SSB transmit, but it uses its own DSP chain rather than WDSP, and does not implement PureSignal.

droidHPSDR aims for the intersection: the WDSP DSP core and radio feature set from deskHPSDR, running on Android, with a touch-first UI.

Design decisions

Audio runs through the radio, not through Android

With a Hermes Lite 2 Plus companion board, mic and speaker audio ride inside the Protocol 1 frames — mic samples up in the EP6 stream, demodulated audio down in EP2, to and from the AK4951 codec on the companion board. The Android audio stack is not in the signal path at all for the primary configuration. No Oboe, no AAudio latency negotiation, no audio policy surprises.

This is the single most important architectural decision in the project. Local Android audio via Oboe is a secondary path for plain HL2 users, planned but not prioritised. Note the tradeoff: the HL2+ requires custom gateware rather than the standard HL2 gateware.

WDSP is kept

PureSignal, the full noise reduction suite, the TX audio chain, and the filter set all live in WDSP. Porting the DSP to something else would mean losing them. WDSP and FFTW3 cross-compile for arm64 with the NDK.

Rendering borrowed, UI not

The waterfall and panadapter use OpenGL ES rather than Cairo. Widgets are Dear ImGui. Both approaches, and much of the Android bootstrap, are informed by SDR++ / SDR++ Brown — but the UI layout is original and aims at a deskHPSDR / Thetis feel, not an SDR++ feel.

Transport is deliberately abstracted

Both wired and wireless are first-class, behind the same interface. Buffer depth is a user setting, defaulting deeper on WiFi.

  • WiFi — the HL2 takes a DHCP lease from the router and is found by the normal Protocol 1 discovery broadcast. Needs a WiFi lock, a foreground service, and a deeper jitter buffer to survive power-save behaviour.
  • USB Ethernet — lowest jitter, preferred for TX. With no DHCP server on the link the HL2 falls back to APIPA at 169.254.19.221 / 255.255.0.0, so the wired path skips discovery and targets it directly.

Android does not self-assign an IPv4 link-local address, so eth0 needs a static address set once by hand (169.254.1.1 / 255.255.0.0). Android persists this per adapter. The HL2's EEPROM fixed-IP option is deliberately not used — it disables DHCP and would break the WiFi path.

The radio keeps running when the app is not on screen

Protocol, DSP, and audio threads must be fully independent of the render loop. The GL surface can stop; the stream cannot. This is a constraint on M1 and M2, not a feature to add later — retrofitting it means rewriting the threading model a second time. Requires a foreground service with a persistent notification, a WiFi lock, and a battery optimisation exemption, or Doze will drop the socket.

The hard part is not any single layer. It is that deskHPSDR does not separate them — GTK types appear inside receiver and transmitter structs, and cross-thread updates go through g_idle_add on a GMainLoop. Untangling that is Milestone 1. GLib without GTK does cross-compile for Android, so keeping GLib and removing only the widget layer is worth attempting before rewriting the threading model.

Roadmap

  1. M0Transport check. Largely answered — SDR++ Brown already reaches this radio from this phone. Only open item is confirming a USB Ethernet adapter takes a static config on the unrooted phone.
  2. M1Headless core. Cross-compile WDSP, FFTW3, and the protocol layer for arm64. Discover, stream, and print S-meter values to logcat. No UI.
  3. M2HL2+ codec loopback. Headless proof that audio into the EP2 slots reaches the companion board's speaker and mic samples arrive in EP6. Validates the whole audio architecture, so it comes before any UI.
  4. M3Picture. Android shell plus GL waterfall.
  5. M4Usable RX. VFO, band, mode, filter, AGC. Enough to actually listen.
  6. M5TX. SSB first, then CW.
  7. M6Extras. IO board I²C, PureSignal, local Oboe audio path.
  8. M7Coexistence. Bluetooth headset support, and running alongside digital mode apps. Parts of this may not be achievable without root.

Wanted, but not solved

Running alongside digital mode apps

The goal is to leave droidHPSDR running in the background while FT8CN, a Winlink client, or similar uses the radio. Android has no virtual audio cable, and the two directions are not equivalent: capturing another app's playback is possible via AudioPlaybackCapture on Android 10+, behind a MediaProjection consent prompt and only where the source app has not opted out, while feeding another app's microphone input has no public API at all — a virtual mic needs root or a system-level HAL.

So a software-only loopback covers at most one direction. The workable approach is to keep the digital audio path physical: HL2+ analog audio to a USB audio interface that the digital app owns directly, while droidHPSDR owns only the network connection. Nothing is shared and nothing is injected. PTT then comes from HL2+ VOX or from the rigctl TCP server inherited from piHPSDR, if the digital app supports network CAT — needs verifying per app. Wired setups will need a powered hub carrying both the Ethernet adapter and the audio interface.

Bluetooth headset audio

Depends on the local Oboe path, since Bluetooth necessarily goes through the Android audio stack rather than the HL2+ codec. Latency decides usability: A2DP is 150–250 ms, acceptable for listening but not for TX monitoring; HFP/SCO is low latency but narrowband mono and poor quality; LE Audio / LC3 is the only genuinely good option, and needs recent hardware on both ends. Likely lands as a listening-only feature first.

Non-goals

  • Small screens below phone size, and Raspberry Pi builds — use piHPSDR.
  • Measurement, IF-tap, or panadapter-only use — use something specialised.
  • Getting merged upstream. deskHPSDR targets desktop macOS and Linux; this is a permanent fork.
